# safeCare 系统规划：家庭保单「条款级」速查系统

> 一句话定位：把家人名下的每一份保险合同，拆成**可溯源的结构化保障要素**，在需要时用一句话问出「这个情况能报吗、报多少、依据是哪一条」。

## 1. 要解决的问题（以及不解决的问题）

保险合同时的真实困难不是「文档长」，而是三件事：

1. **结论散落在多处**：保额在保险单页，赔付比例在条款第 X 条，范围限制在释义里，等待期在特别约定里。
2. **表述不统一**：「年免赔额」「绝对免赔额」「每次事故免赔」是三个词一件事；同一份医疗险对不同就医情形有不同比例。
3. **无法自证**：网上/AI 给的答案对不对，没人敢在住院前去信。

因此系统的**第一性要求是溯源**：任何一条结论都必须能点回到原文的页码 + 条款号 + 原句。抽不出来就明确标记「未识别/待确认」，绝不猜。

**明确不做**：不替代理赔核定、不预测能否赔付、不提供法律意见。系统给的是「条款怎么说 + 需要你自己确认什么」。

## 2. 核心使用场景

| # | 场景 | 系统应产出 |
|---|---|---|
| S1 | 家人住院了，手里有 3 份保单，分别能报多少 | 按成员聚合的「报销路径」：哪份先报、免赔额、比例、限额、剩余缺口 |
| S2 | 这个检查/药品/治疗方式是否在范围内 | 条款级判断 + 免责条款命中提示 + 原文引用 |
| S3 | 刚买 40 天出险，能赔吗 | 等待期、犹豫期、生效日、既往症条款的准确日期与结论 |
| S4 | 一年到底买了什么 | 家庭保障总览：保额、险种、到期日、续费提醒、明显缺口 |
| S5 | 两份医疗险是不是重复了 | 报销型/给付型属性对比 + 是否可叠加 |
| S6 | 换工作时社保断了，保险有影响吗 | 有社保/无社保版本的比例差异（条件化数值） |
| S7 | 四类保单叠在一起，身故/医疗到底能拿几份 | 报销型 vs 给付型标注 + 身故责任重叠提示 |
| S8 | 意外摔伤看门诊，用意外医疗还是百万医疗 | 两份保单的免赔额/比例/范围并排对比 |

## 3. 设计原则

- **P1 条款单元是数据的最小单位**，不是整份 PDF，也不是整页。所有结构化字段挂到 `clause` 上。
- **P2 引用必须可校验**：模型输出的每段 `quote` 都要能在对应 `clause.text` 里定位到（归一化后模糊匹配），校验不过的字段直接降级为待复核。
- **P3 条件化数值**：比例/限额/免赔额不是单值，是「在什么前提下等于多少」。数据结构必须能表达这个。
- **P4 条款册与保单分离**：同一产品的条款册会被多张保单复用，解析一次、引用多次（省钱、也保证一致）。
- **P5 幂等 + 版本化**：文件按 sha256 去重；条款随产品版本升级，结论要绑定「当时生效的条款版本」。
- **P6 隐私默认本地**：保单含姓名、身份证、健康状况。默认本机存储、本机推理；一旦走云端模型，先做占位符脱敏。

## 4. 数据模型

```
member            家庭成员（本人/配偶/子女/父母）
 └ document       上传的文件（原件 + 页面文本/图像）
    └ clause      条款单元（页码区间、条款号、章节路径、分类、原文）
    └ policy      保单（一张保单 = 一个被保险人在一家公司的一个产品）
       ├ coverage  保障责任项（可多项：住院/门诊/特药/质子重离子…）
       ├ exclusion 责任免除项
       └ term      其他关键约定（等待期/续保/退保/犹豫期…）
```

关键表（SQLite）：

```sql
member(id, name, relation, birth_date, sex, notes)

document(id, member_id, sha256 UNIQUE, filename, page_count,
         text_layer ENUM('text','scan','mixed'), status, created_at)

page(document_id, page_no, width, height, text, ocr_engine, ocr_confidence)

-- 条款复用：product 级别，不代表具体某张保单
clause_set(id, insurer, product_name, version, effective_from)

clause(id, clause_set_id, seq, page_from, page_to, clause_no,
       heading_path,          -- 如 "第三部分 > 保险责任 > 第5条"
       category,              -- 保险责任/责任免除/释义/等待期/理赔/合同解除/其他
       text, char_start, char_end)

policy(id, document_id, clause_set_id, member_id,
       insurer, product_name, category,   -- 医疗/重疾/意外/寿险/年金
       policy_no, holder_name, insured_name,
       effective_from, effective_to, premium, premium_freq, status)

coverage(id, policy_id, name, benefit_type,   -- 报销型/给付型
         limit_amount, currency, deductible,
         tiers JSON,          -- [{when:"经社保结算", ratio:1.0, limit:null}, …]
         waiting_days, hospital_scope, drug_scope,
         condition_text, citation_clause_id,
         confidence, review_status)

exclusion(id, policy_id, category, text, citation_clause_id, confidence)
term(id, policy_id, kind, value, citation_clause_id, confidence)

extraction_run(id, document_id, stage, engine, model, prompt_version,
               tokens, cost, status, started_at, finished_at, error)
```

`tiers` 是最容易被做错的地方，示例：

```json
[
  { "when": "经社保结算", "ratio": 1.0, "limit": 1000000 },
  { "when": "未经社保结算", "ratio": 0.6, "limit": 1000000 },
  { "when": "院外特药", "ratio": 1.0, "limit": 200000, "separate_limit": true }
]
```

**字段字典**（跨公司口径统一，抽取前先定义，抽取时按此归一；逐字段口径、JSON Schema 草案与归一表述对照见 [`docs/FIELDS.md`](./FIELDS.md)）：

- 医疗险（报销型）：年度限额 / 分项限额 / 免赔额（年|次|家庭共享）/ 赔付比例（分档）/ 等待期 / 医院范围（公立普通部|特需|私立）/ 药品范围（社保内|外|院外特药）/ 住院前后门急诊天数 / 特殊门诊 / 门诊手术 / 续保条件（保证续保 X 年|非保证）/ 既往症。
- 重疾险（给付型）：保额 / 病种数 / 重疾·中症·轻症比例与次数 / 是否分组 / 间隔期 / 特定疾病额外赔 / 癌症二次赔 / 身故责任 / 保费豁免 / 等待期。
- 意外险：意外身故保额 / 意外伤残保额与 1–10 级比例表 / 意外医疗（限额·免赔·比例·是否限社保内）/ 住院津贴 / 猝死是否附加 / 交通额外赔 / 职业类别限制 / 生效时间。
- 寿险：身故·全残保额（是否共用）/ 保险期间 / 等待期及意外是否免等待 / 免责条数 / 现金价值·保单贷款·减额交清 / 受益人。

## 5. 处理流水线

```
上传 → 指纹去重 → 版面解析 → 条款切分 → 条款分类 → 按险种模板抽取 → 校验 → 入库 → 检索索引
                                                                    └→ 待复核队列
```

每个 stage 落 `extraction_run`，可单独重跑，失败不影响已完成的 stage。

**S1 解析**
- 有文本层：`pdfjs-dist` 取逐页文本 + 坐标（保留页码、行序，用于后续定位与高亮）。
- 无文本层（扫描件）：页面渲染 PNG → 本地 OCR（RapidOCR / PaddleOCR，中文模型）→ 保留行框坐标。
- 表格单独走表格抽取，不要和正文混在一段文字里（免赔额、比例表多在此处，最容易错位）。

**S2 条款切分**（规则版已实现：`lib/segmentation.ts`，回归测试 `tests/segmentation.test.ts`）

真实保单（人保寿险少儿长期医疗险，44 页合同 / 37 页条款）暴露的结构问题：

| 实际现象 | 若按想当然的规则 | 采用的规则 |
|---|---|---|
| 编号是 `2.5 保险责任`，**不是「第X条」** | 按「第X条」写会一条都切不出来 | 认 `\d+(\.\d+)*` + 标题 |
| 标题被换行截断：`2.3 保险金额与` / `给付限额` | 标题只剩半句，分类全错 | 上行以「与/和/或/及」结尾，或下行极短且再下行已是正文 → 拼接 |
| 脚注 `4 重大疾病：名称列表见…` 混排在正文流里 | 释义/免责被算进上一条 | 页内遇「小号数字 + 术语 + 冒号」进入脚注态，直到下一页页眉或下一个小节号 |
| 两套页码：合同 `第5页，共44页`、条款册 `条款正文第 1 页 /共 37 页` | 引用定位会指错页 | 物理页号入库，印刷页码另行保留；只从条款册页眉开始切 |
| 章节号连续（1…9，小节 .1 递增） | —— | 当作强约束：`1 年`、`30 日` 这类正文不会被误判成标题 |
| 免赔额/给付比例在「附表1 保障表」的表格里 | 正文里根本抽不到 | 附表单独成条（`附表N`），表格抽取另做 |

- 切分只到 `N.M` 一级；`（一）（二）` 属于条款内部结构，保留为正文，不单独成条。
- **覆盖率** = 归入条款的字符 / 条款册全部字符。低于 ~90% 说明有正文被漏掉（封面语、目录残留、脚注误判），直接显示在界面上。
- 规则搞不定的部分再交给 LLM 做「段落序列」二次切分，输出 `{start_para, end_para, clause_no, heading}`，只切分不做摘要。

**S3 分类**：每条 clause 打一个 `category`。小模型/规则即可，重点是**保险责任、责任免除、释义**三类不能错——后面的抽取和问答都依赖它。

**S4 抽取**
- 按险种模板选 schema，只把该保单相关的 clause（含释义中出现的术语）拼进上下文，不塞整本。
- 分两遍：先抽「保障责任列表」（有哪些责任项），再对每个责任项抽「限额/免赔/比例/条件」，避免一次输出过长导致漏项。
- 强制 JSON Schema 输出 + `citation_clause_id` 必填；抽不到就 `null` + `review_status='needs_review'`。
- 数字规范化：`100万`→`1000000`（人民币元），`100%`/`100`（百分数）统一，日期统一 `YYYY-MM-DD`。

**S5 校验**（无需模型，纯规则，性价比最高）
- quote 能在 clause 原文中定位（阈值 0.9）。
- `deductible <= limit`、`0 <= ratio <= 1`、`effective_from < effective_to`、等待期 ≤ 保险期间。
- 分项限额之和 ≤ 年度限额，否则标记冲突。
- 同一字段在多个 clause 出现且不一致 → 保留两条并标记 `conflict`，交人工。

## 6. 检索与问答

- 索引：SQLite FTS5（中文用 `simple` 分词器 + 自建 bigram 方案）+ 向量（本地 `bge-m3` / `bge-small-zh`，ONNX 推理，不联网）。
- 混合打分：BM25 与向量做 RRF 融合，按 `member / policy / clause_category` 加过滤条件。
- 回答流程固定为四步：**检索 → 组织证据 → 生成 → 引用校验**。校验不过就退化成「列出相关条款原文」，不给结论。
- 拒答条件：检索不到、命中条款互相矛盾、问题要求判断「赔不赔」（改为给出核定要件清单）。
- 输出结构固定：`结论要点 / 计算过程 / 依据（可点击到原文）/ 需你确认的不确定项`。

## 7. 前端信息架构

1. **家庭总览**：成员卡片 → 保单数、险种覆盖、最近到期、待复核项数量。
2. **保单详情**：顶部「速查卡」（8–12 个关键指标，一屏看完）；下方双栏：左原文、右结构化。点字段 → 原文滚动并高亮。
3. **条款浏览器**：按分类折叠（保险责任 / 免责 / 释义 / 理赔流程），支持全文搜索。
4. **问答**：答案 + 引用卡片 + 不确定项清单。
5. **待复核队列**：所有 `needs_review` 字段集中处理，左侧原文右侧输入框——这是保证数据质量的核心界面，MVP 不能省。
6. **对比**：同成员多份同类保单的关键指标表格（免赔额/比例/限额/续保）。

## 8. 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 应用 | Next.js (App Router) + TypeScript + Tailwind + shadcn/ui | 单进程全栈，PDF 预览与高亮好做，后续可迁 Sites |
| 存储 | SQLite（Drizzle ORM）+ 本地目录 `data/`（原件、页面图） | 单机零运维；全文检索用 FTS5；后续可换 D1/R2 |
| PDF | `pdfjs-dist`（文本层 + 页面渲染） | 浏览器/服务端一致，坐标可用于高亮 |
| OCR | MVP 不做；后续按需接 RapidOCR / PaddleOCR | 已确认全为电子保单（有文本层），少一个本地 Python 依赖 |
| 抽取 | DeepSeek 云 API（OpenAI 兼容），调用前强制脱敏 | 中文长文本理解好、单价低；适配层保留换模型能力 |
| 向量 | `bge-small-zh` / `bge-m3`（ONNX，本地） | 不出网、免费、中文够用 |
| 部署 | 阶段一：本机 `localhost`；阶段二：家庭云（鉴权 + 家庭共享） | 先解决自己用，再解决家人用 |

**抽取适配层接口**（三种实现可替换）：

```ts
interface Structurer {
  extract<T>(args: {
    schema: JSONSchema;      // 险种模板
    clauses: ClauseContext[]; // 带 id 的条款
    task: 'coverage_list' | 'coverage_detail' | 'metadata' | 'exclusions';
  }): Promise<{ data: T; usage: { tokens: number } }>;
}
```

### 8.1 脱敏（走云 API 时的硬前置）

原则：**只抹掉「谁」，绝不改动「条款说了什么」**。条款正文、病种定义、免责表述必须原样发送，否则模型无法判断保障范围；姓名、证件号这类直接标识符则一律不出本机。

| 类型 | 处理 | 识别方式 |
|---|---|---|
| 姓名（被保险人/投保人/受益人） | `‹NAME_1›` `‹NAME_2›` | 家庭名册 + 保单元信息 + 中文姓名正则 |
| 身份证 / 护照 | `‹ID_1›` | 18 位身份证校验位正则 |
| 手机号 / 固话 | `‹PHONE_1›` | 正则 |
| 保单号 / 银行卡号 | `‹POLICY_NO_1›` `‹CARD_1›` | 正则 + 保单元信息 |
| 住址 | `‹ADDR_1›` | 正则 + 关键词（省/市/区/路/号） |
| 邮箱 / 微信 | `‹CONTACT_1›` | 正则 |

规则：

1. 同一文档内同一实体用同一占位符，跨文档重新编号，避免通过编号关联家庭成员。
2. 映射表只存本地库（`redaction_map`），**不随请求发送、不写日志**。
3. 发送前做一次**出口校验**：payload 仍命中身份证/手机号/银行卡正则就直接阻断，记 `redaction_blocked`，宁可不抽。
4. 只记录 token 用量与文档 hash，不落原始 prompt；返回结果回填占位符后再入库。
5. 界面上每个保单详情页显式展示「本次调用上传了哪些字段结构」（不展示原文），让用户知道自己交出了什么。

## 9. 里程碑

| 阶段 | 交付 | 验收标准 |
|---|---|---|
| M0 骨架 | 上传、指纹去重、文本层提取、逐页预览、SQLite schema | 丢进 3 份电子保单，能看到原文与页数，刷新不丢 |
| M1 条款化 ✅ 规则版 | 条款切分 + 分类 + 保单元信息抽取 + 目录对账（`lib/segmentation.ts` / `lib/policy-meta.ts` / `lib/toc.ts`） | 条款册覆盖率 ≥ 90%；等级编号（1.1/2.5）正确率 ≥ 95%；切出条数与条款目录一致 |
| M2 结构化·医疗与重疾 ✅ | 附表保障表（`lib/benefit-table.ts`）→ `coverage`；AI 增补（`lib/ai/`）→ `clause_ai` + `exclusion`/`term`（`source='ai'`）；速查卡（报不报 / 报多少 / 还得满足什么）；点 P 页码跳原文并高亮引文；待复核队列（`review_status='needs_review'`） | 关键字段（限额/免赔/比例/等待期）准确率 ≥ 90%，全部带可点击引用 |
| M3 结构化·意外与寿险 | 复用 M2 流水线与 schema 包，补意外/寿险模板与跨险种事实标签 | 意外医疗三项（限额·免赔·比例）≥ 92%；寿险核心字段 ≥ 95% |
| M4 问答 | 混合检索 + 问答 + 引用校验 + 拒答 | 30 条真实问题上，引用命中率 ≥ 95%，无引用结论数 = 0 |
| M5 家庭视角 | 家庭总览、同险种对比、报销/给付叠加分析、到期提醒、（可选）报销试算 | 一名成员 4 类保单可在 1 屏内比较并看出可叠加项 |

MVP 边界：先支持**文本层 PDF**，四类险种全部纳入（医疗/重疾字段最多、先落地；意外/寿险字段少，紧随其后）。扫描件 OCR、年金、分红/万能结算利率、团险不做。

## 10. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 扫描件 / 双栏 / 表格错位 | 免赔额、比例错得很隐蔽 | 表格独立抽取；数字类字段强制规则校验；低置信进复核 |
| 一份文件含多张保单、多份条款册 | 责任挂错保单 | 解析出「保险单页」与「条款册」两类，条款册建 `clause_set` 复用 |
| 模型幻觉补充条款没写的内容 | 最危险的错误 | quote 反查校验 + 强制 `null` + 拒答策略 |
| 条款版本更新（保证续保、特药清单） | 旧结论误导 | 条款版本化 + 结论绑定版本 + 变更提示 |
| 隐私 | 家庭健康信息泄露 | 默认本地推理；云调用前脱敏；`data/` 不入 git；导出/删除能力 |
| 用户过度信任 | 决策风险 | 每条结论固定显示「依据原文 + 需确认项」，页脚常驻免责声明 |

## 11. 评测

建 `eval/gold.jsonl`：20–30 份真实保单（覆盖 3–4 家公司、四类险种齐全，含 1–2 份扫描件），人工标注：

```
{doc, field, expected_value, clause_no, page}
```

指标：条款切分召回率、字段精确匹配率、引用定位命中率、无依据断言数（必须为 0）、问答人工 1–5 分。每次改 prompt 或换模型跑一遍，避免「感觉变好了」。

切分这一层不必等人工标注：合同自带的「条款目录」就是这份文件的金标准，用 `lib/toc.ts` 直接对账，漏条和错号当场可见。
